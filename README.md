# 대흥CNS 기업 홈페이지 구축 프로젝트

## 1. 프로젝트 목표

산업용 포장자재 제조·가공 및 납품 기업인 대흥CNS의 공식 홈페이지를 구축한다.

홈페이지의 핵심 목표는 다음과 같다.

1. 기업 고객에게 회사의 신뢰도와 제조 기반을 전달한다.
2. 비닐·필름, 테이프, 랩 제품을 직관적으로 탐색할 수 있게 한다.
3. 고객이 제품별 견적 및 구매 문의를 쉽게 남길 수 있게 한다.
4. 접수된 문의가 유실되지 않도록 서버 DB에 저장하고 회사 이메일로 알림을 발송한다.
5. 관리자가 지속적인 홈페이지 관리에 많은 시간을 쓰지 않아도 운영할 수 있도록 한다.

**중요한 운영 정책**

초기 버전은 PG 결제, 장바구니, 자동 주문 확정 기능을 제공하지 않는다.

제품별 생산 가능 여부, 최소 주문 수량, 원료 수급 상황, 단가 및 납기가 달라질 수 있으므로 모든 거래는 담당자의 확인 후 확정한다.

이 프로젝트는 일반적인 온라인 쇼핑몰이 아니라 B2B 제품 카탈로그와 견적 문의 시스템이다.

## 2. 회사 정보

회사명: 대흥CNS

주요 사업: 산업용 포장자재 제조·가공 및 납품

핵심 제품군:

- 비닐 및 플라스틱 필름
- 산업용 테이프
- 랩 및 스트레치필름
- 기타 산업용 포장자재

확인된 사업 및 설비 관련 이력:

- 2015년 100mm 압출기 추가 설비
- 2017년 제2공장 부지 및 건물 확보
- 2021년 60mm 압출 설비 증설

확인된 거래 및 납품 이력에는 현대모비스, 현대·기아자동차, 대한항공, 삼성물산, 아시아나에어포트, 금호타이어, SPC그룹, 존슨콘트롤즈오토모티브코리아, 베트남 세화비나 및 멕시코 관련 법인 납품 등이 있다.

2014년 현대모비스 우수업체 선정 및 수상 이력, 2017년과 2022년 모범납세자 표창 이력, 2017년 기술평가 우수기업 인증 이력, 2020년 GRS 인증 관련 이력이 있다.

거래처 명칭, 로고, 인증서, 인증 유효 여부 및 공개 가능 범위는 실제 자료를 확인한 뒤 게시한다.

확인되지 않은 설립 연도, 주소, 전화번호, 이메일, 생산 능력, 인증 유효성, 품질 인증, 고객사 로고 사용 권한은 임의로 만들어내지 않는다.

미확정 정보는 별도 설정 파일 또는 관리자 편집 데이터로 분리하고, 실제 정보가 입력되기 전에는 공개하지 않는다.

## 3. 기술 스택 및 구현 원칙

프로젝트가 이미 존재하면 기존 기술 스택과 코드 구조를 먼저 확인하고 최대한 유지한다.

신규 프로젝트라면 다음을 기본안으로 사용한다.

- Next.js App Router
- TypeScript
- Tailwind CSS
- 재사용 가능한 UI 컴포넌트
- 서버 측 문의 접수 API
- MySQL 기반 데이터베이스
- AWS를 이용한 DB 및 필요시 관리자 인증
- Resend 또는 동등한 트랜잭션 이메일 서비스
- 환경변수로 비밀 정보 관리

현재 프로젝트의 구조와 배포 환경을 먼저 조사한 후 구현 계획을 설명한다. 기존 프로젝트가 없다면 위 스택으로 초기화한다.

API 키, 이메일 API 키, DB 접속 정보는 절대로 프론트엔드 코드에 노출하지 않는다.

실제 서비스와 연결되지 않은 기능을 완성된 기능인 것처럼 표시하지 않는다.

## 4. 전체 페이지 구조

다음 페이지를 구현한다.

### 4-1. 메인 페이지 `/`

구성 순서:

1. 헤더 및 네비게이션
2. 메인 히어로 영역
3. 주요 제품 카테고리
4. 대흥CNS의 핵심 경쟁력
5. 제조 설비 및 생산 기반 소개
6. 주요 거래·납품 이력
7. 주요 연혁
8. 견적 문의 CTA
9. 푸터

메인 헤드라인 예시:

"산업 현장을 이해하는 포장자재 파트너, 대흥CNS"

서브 카피 예시:

"비닐·필름부터 테이프와 스트레치필름까지. 고객의 사용 목적과 요구 규격에 맞는 포장자재 공급 방안을 상담합니다."

CTA:

- 제품 둘러보기
- 견적 문의하기
- 전화 상담

생산 능력, 최저가, 당일 출고, 빠른 납기 등 확인되지 않은 주장을 사용하지 않는다.

### 4-2. 제품 목록 페이지 `/products`

제품을 카테고리별로 분류한다.

카테고리:

- 전체
- 비닐·필름
- 테이프
- 랩·스트레치필름
- 기타 포장자재

제품 카드에는 다음 정보를 표시한다.

- 제품 이미지
- 제품명
- 한 줄 설명
- 주요 용도
- 확인된 규격 또는 상담 가능 항목
- 견적 문의 버튼

필수 UX:

- 카테고리 필터
- 제품명 검색
- 반응형 카드 레이아웃
- 명확한 제품명과 용도
- 제품별 견적 문의 CTA

가격이 확정되지 않은 제품은 가격을 임의로 표시하지 않는다. 가격 영역 대신 "규격 및 수량에 따라 견적"이라고 표시한다.

검색 결과가 없으면 적절한 안내 문구와 전체 제품 보기 기능을 제공한다.

### 4-3. 제품 상세 페이지 `/products/[slug]`

제품별 상세 페이지를 제공한다.

표시 정보:

- 제품명
- 대표 이미지 및 추가 이미지
- 제품 설명
- 주요 용도
- 확인된 규격
- 색상 및 형태 등 선택 가능한 옵션
- 상담 시 확인할 항목
- 견적 문의 버튼
- 관련 제품

제품 데이터는 별도의 데이터 파일 또는 DB로 관리한다.

제품별 상세 내용을 컴포넌트에 하드코딩하지 않는다.

제품 규격과 옵션은 확인된 정보만 공개하며, 확인되지 않은 규격은 "별도 문의"로 처리한다.

제품 상세 페이지에서 문의하기를 클릭하면 해당 제품명이 문의 폼에 자동 입력되도록 한다.

### 4-4. 회사 소개 페이지 `/about`

구성:

- 회사 소개
- 사업 분야
- 생산 기반 및 설비 관련 이력
- 기업 연혁
- 인증 및 수상 이력
- 주요 납품 분야
- 견적 문의 CTA

회사 연혁은 연도별 타임라인 형태로 구성한다.

연혁 데이터는 다음 필드를 가진 구조화된 데이터로 관리한다.

- year
- month
- title
- description
- category

카테고리는 설비 확충, 납품 계약, 인증 및 수상 등으로 구분한다.

연혁은 최신순 또는 과거부터 순서대로 읽기 쉽게 표시하고, 모바일에서도 날짜와 내용이 명확하게 구분되어야 한다.

### 4-5. 견적 문의 페이지 `/contact`

다음 정보를 입력받는다.

필수:

- 담당자 연락처
- 개인정보 수집·이용 동의

선택:

- 회사명
- 담당자명
- 이메일
- 제품 카테고리
- 제품명
- 희망 규격
- 예상 수량
- 희망 납기
- 납품 지역
- 추가 요청 사항
- 제품 사진 또는 규격서 첨부

문의는 제품 상세 페이지에서 진입할 경우 제품 정보가 자동으로 입력되어야 한다.

고객이 규격이나 수량을 정확히 모르는 경우에도 상담을 요청할 수 있어야 한다.

첨부파일은 허용된 파일 형식과 크기를 제한하고 안전하게 저장한다. 파일 업로드가 구현되지 않았다면 첨부 기능이 있는 것처럼 표시하지 않는다.

### 4-6. 개인정보 처리방침 `/privacy`

문의 접수에 필요한 개인정보 수집·이용 안내와 개인정보 처리방침을 제공한다.

실제 운영 주체, 개인정보 수집 항목, 목적, 보유 기간, 처리 위탁 여부 등을 확인한 뒤 정확하게 작성한다.

법적 검토가 필요한 내용을 임의로 확정하지 않는다.

## 5. 문의 접수 및 이메일 알림

문의 시스템은 프로젝트의 핵심 기능이다.

### 5-1. 데이터베이스

`inquiries` 테이블을 생성한다.

권장 필드:

- id: UUID
- inquiry_number: 사람이 읽기 쉬운 문의 번호
- company_name
- contact_name
- phone
- email
- product_category
- product_name
- specification
- quantity
- desired_delivery_date
- delivery_location
- message
- attachment_path
- privacy_consent
- status
- created_at
- updated_at
- email_notification_status
- email_notification_attempts
- email_notification_last_error
- internal_note

상태값:

- NEW: 신규 문의
- REVIEWING: 검토 중
- WAITING_CUSTOMER: 고객 답변 대기
- QUOTED: 견적 안내 완료
- COMPLETED: 처리 완료
- CANCELLED: 취소

DB에 문의가 저장되는 것을 접수 성공의 기준으로 삼는다.

이메일 발송 성공 여부와 문의 접수 성공 여부를 분리한다.

이메일 발송에 실패하더라도 저장된 문의를 삭제하거나 고객에게 문의 접수가 실패했다고 단정하지 않는다.

문의 번호는 서버에서 생성하며 중복되지 않아야 한다.

### 5-2. 문의 접수 처리 흐름

1. 고객이 문의 폼을 제출한다.
2. 서버에서 입력값을 검증한다.
3. 개인정보 동의 여부를 확인한다.
4. 스팸 및 악의적인 입력을 검사한다.
5. DB에 문의를 저장한다.
6. 저장 성공 후 회사 이메일로 알림을 발송한다.
7. 이메일 발송 상태를 기록한다.
8. 고객에게 문의 번호와 접수 완료 화면을 보여준다.

DB 저장이 실패하면 접수 성공 화면을 보여주지 않는다.

DB 저장에 성공했지만 이메일 발송에 실패했다면 접수는 완료된 것으로 처리하고, 이메일 알림 실패를 별도로 기록하여 관리자가 확인할 수 있게 한다.

### 5-3. 회사 이메일 알림

회사 이메일 주소는 환경변수로 관리한다.

예시:

- `INQUIRY_NOTIFICATION_EMAIL`
- `EMAIL_FROM`
- `RESEND_API_KEY`

실제 주소와 발신 도메인은 운영 환경에서 설정한다.

이메일 제목 예시:
`[대흥CNS 홈페이지] 신규 견적 문의 - 문의번호`

이메일 본문에는 다음 정보를 표시한다.

- 문의 번호
- 접수 일시
- 회사명
- 담당자명
- 연락처
- 제품명 및 카테고리
- 규격
- 수량
- 희망 납기
- 납품 지역
- 추가 요청 사항
- 관리자 페이지에서 문의 확인하기 링크

이메일 발송은 서버 측에서 수행한다.

이메일 발송 실패 시 재시도할 수 있도록 구성하고, 실패 상태와 오류를 기록한다.

재시도는 중복 이메일을 고려해 설계한다.

관리자가 별도 조치를 하지 않아도 신규 문의가 이메일로 전달되는 구조를 우선한다.

### 5-4. 고객 접수 완료 화면

접수 완료 화면에는 다음을 표시한다.

- 문의 접수 완료
- 문의 번호
- 접수 내용 요약
- 담당자가 생산 가능 여부 및 견적을 확인한 후 연락한다는 안내
- 회사 전화번호
- 메인으로 돌아가기

"주문 완료", "구매 확정", "출고 확정" 등의 표현을 사용하지 않는다.

문의 접수는 구매 계약이나 생산 확정을 의미하지 않는다.

## 6. 관리자 페이지 `/admin`

운영자가 문의를 관리할 수 있는 간단한 관리자 페이지를 구현한다.

관리자 인증을 반드시 적용하며, 관리자 계정이나 비밀번호를 소스 코드에 하드코딩하지 않는다.

기능:

- 문의 목록 조회
- 신규 문의 수 표시
- 상태별 필터
- 문의 번호 및 제품명 검색
- 접수일 기준 정렬
- 문의 상세 보기
- 연락처 및 이메일 확인
- 처리 상태 변경
- 내부 메모 작성
- 문의 내역을 CSV로 내보내기
- 이메일 알림 발송 상태 확인

미처리 문의를 눈에 띄게 표시한다.

관리자 페이지가 없어도 이메일만으로 문의를 확인할 수 있어야 하지만, 문의 DB를 조회하고 처리 상태를 관리하는 기능은 제공한다.

문의 삭제는 실수로 기록이 사라지는 것을 방지하도록 신중하게 설계한다.

관리자 페이지의 접근 권한과 개인정보 보호를 고려한다.

## 7. 디자인 시스템

디자인 방향은 신뢰감 있고 현대적인 산업용 B2B 기업 홈페이지다.

디자인 원칙:

- 화이트 배경
- 네이비 중심의 브랜드 컬러
- 차분한 회색 보조 색상
- 충분한 여백
- 일관된 타이포그래피
- 직관적인 제품 카드
- 명확한 제목과 CTA
- 과도한 애니메이션 금지
- 읽기 쉬운 한글
- 모바일 우선 반응형 설계

제품은 이미지, 제품명, 용도, 문의 버튼을 중심으로 보여준다.

메인 페이지에서는 제품 탐색과 문의 기능을 쉽게 찾을 수 있어야 한다.

제품 목록에서 문의 버튼까지 이동하는 데 불필요한 단계가 없어야 한다.

이미지가 없는 경우 레이아웃이 깨지지 않도록 대체 이미지를 제공한다.

실제 회사 로고와 제품 이미지는 교체하기 쉽게 별도 파일 또는 데이터로 관리한다.

임시 이미지와 실제 회사 사진을 혼동하지 않도록 한다.

## 8. 모바일 UX

모바일 환경에서도 모든 기능을 사용할 수 있어야 한다.

- 모바일 내비게이션
- 제품 카드의 적절한 열 수 조정
- 폼 입력 요소의 충분한 터치 영역
- 전화번호 클릭 시 전화 앱 실행
- 이메일 클릭 시 메일 앱 실행
- 하단 고정 전화 문의 및 견적 문의 버튼
- 모바일에서 가로 스크롤이 발생하지 않는 레이아웃

전화번호가 설정되지 않은 상태에서는 임의의 번호를 연결하지 않는다.

## 9. SEO 및 접근성

다음을 적용한다.

- 페이지별 고유한 title 및 description
- 의미 있는 URL 구조
- Open Graph 메타데이터
- sitemap.xml
- robots.txt
- 시맨틱 HTML
- 이미지 alt 텍스트
- 키보드 탐색 지원
- 명확한 폼 라벨
- 필수 항목 및 오류 메시지 표시
- 적절한 대비와 글자 크기

주요 검색 키워드는 산업용 비닐, 방청비닐, PE 비닐, OPP 테이프, 스트레치필름, 산업용 포장자재 등을 자연스럽게 활용한다.

실제 제품 취급 여부가 확인되지 않은 키워드를 확정적인 판매 문구로 사용하지 않는다.

## 10. 보안 및 운영 안정성

- 서버 측 입력값 검증
- 스팸 방지
- 요청 빈도 제한
- SQL 인젝션 방지
- XSS 방지
- CSRF 등 해당 환경에 필요한 요청 위조 방어
- 파일 업로드 검증
- 비밀 정보의 환경변수 관리
- 관리자 인증 및 접근 제어
- 개인정보 최소 수집
- DB 백업 및 복구 계획
- 오류 로그
- 이메일 발송 실패 기록
- 운영 환경과 개발 환경 분리

개인정보와 문의 내용이 불필요하게 로그에 노출되지 않도록 한다.

문의 접수 API를 공개할 경우 스팸 및 자동화된 반복 제출에 대한 방어를 구현한다.

## 11. 실제 배포 및 환경 설정

환경변수 예시 파일 `.env.example`을 제공한다.

필요한 값의 예:

- DATABASE_URL
- RESEND_API_KEY
- EMAIL_FROM
- INQUIRY_NOTIFICATION_EMAIL
- ADMIN_AUTH 관련 설정

실제 비밀 값은 저장소에 커밋하지 않는다.

DB 마이그레이션 파일을 제공하고 신규 환경에서 재현 가능하도록 한다.

README에 다음을 설명한다.

- 개발 환경 실행 방법
- DB 생성 및 마이그레이션
- 이메일 서비스 연결 방법
- 발신 도메인 인증
- 환경변수 설정
- 관리자 계정 설정
- 테스트 방법
- 배포 방법
- 문의 데이터 백업 및 복구 방법

이메일 발송 도메인과 실제 수신 주소가 설정되지 않은 경우 그 사실을 명확하게 안내한다.

## 12. 테스트 및 완료 조건

다음 항목을 검증한다.

1. 메인 페이지와 모든 주요 페이지가 정상 표시된다.
2. 카테고리 필터 및 제품 검색이 동작한다.
3. 제품 상세 페이지에서 문의 폼에 제품 정보가 전달된다.
4. 유효하지 않은 입력은 서버에서 거부된다.
5. 필수 동의가 없는 경우 문의 접수가 차단된다.
6. 문의가 DB에 정상 저장된다.
7. DB 저장 실패 시 성공 화면이 표시되지 않는다.
8. DB 저장 성공 후 이메일 알림이 발송된다.
9. 이메일 발송 실패 상태가 기록된다.
10. 고객에게 접수 번호가 표시된다.
11. 관리자 인증 없이는 문의 내역에 접근할 수 없다.
12. 관리자 상태 변경이 정상적으로 저장된다.
13. 모바일 및 데스크톱에서 화면이 정상 표시된다.
14. 존재하지 않는 제품 및 잘못된 URL에 적절한 안내를 제공한다.
15. 실제 운영에 필요한 환경변수와 설정이 문서화되어 있다.

테스트용 이메일이나 DB 연결만 구성한 상태를 실제 운영 가능한 완성 상태라고 주장하지 않는다.

## 13. 구현 진행 방식

다음 순서로 작업한다.

1. 기존 프로젝트와 파일 구조 확인
2. 필요한 페이지 및 컴포넌트 설계
3. 디자인 시스템과 공통 레이아웃 구현
4. 회사 소개, 연혁, 제품 데이터 구현
5. 제품 목록 및 상세 페이지 구현
6. 문의 폼과 서버 API 구현
7. DB 스키마 및 마이그레이션 구현
8. 이메일 알림 연결
9. 관리자 페이지 구현
10. 반응형, SEO, 접근성 개선
11. 기능 테스트 및 오류 수정
12. 배포 및 운영 설정 문서 작성

각 단계가 끝나면 구현 결과와 미완성 항목을 명확하게 보고한다.

작업을 시작하기 전에 구현 계획과 주요 데이터 구조를 간단히 제시한다.

가능한 경우 전체 페이지를 먼저 구현해 디자인 방향을 확인한 후 세부 기능을 연결한다.

실제 회사 정보가 필요한 부분은 임의로 채우지 말고 설정값 또는 교체 가능한 데이터로 분리한다.

최종 목표는 시각적으로 완성도 높은 홈페이지이면서, 실제 운영 환경에서 문의 누락을 최소화하고 담당자의 업무 부담을 줄이는 B2B 기업 홈페이지를 구축하는 것이다.
